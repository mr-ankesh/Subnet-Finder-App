## Key Decisions

- Additive layer, not a migration — `advisor/session_store.py` and every
  route from the two prior advisor phases are completely untouched;
  `ADVISOR_CHAT_HISTORY_ENABLED` switches which UI renders. Migrating the
  old routes onto the new schema is deliberately deferred (`next-actions.md`
  item 19).
- `kb_version` is a single hand-bumped constant, not a live aggregate of
  every KB file's own version — an honest scope limit given
  `catalog_loader`'s process-wide `lru_cache` and the absence of any
  versioned KB storage to actually replay history against.
- Correction detection runs BEFORE classification, as a deterministic
  regex check — not dependent on the LLM classifier correctly recognizing
  "actually, make it 20 VMs" as freeform.

## Key Decisions (KB management)

- DB overrides live in the DB, not on disk — `advisor_kb/` is baked into
  the container image and prod runs 3 replicas by rebuild, so a disk
  write would neither persist nor stay consistent across pods.
- `contextvars`-based pinning over threading an explicit version id
  through every engine function — the engines are already pure functions
  of a state dict called from many places across three prior advisor
  phases; re-plumbing all of them for one cross-cutting concern would
  have touched far more surface than the pin itself needed.
- `POST /api/admin/advisor-kb/activate` re-validates the re-submitted zip
  from scratch rather than trusting a stashed result from an earlier
  `/validate` call — no server-side stash needed (correct under 3
  replicas with no in-process affinity), and closes the gap where the KB
  or the uploaded file could have changed between the two calls.
