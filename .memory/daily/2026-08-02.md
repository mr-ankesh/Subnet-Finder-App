- **Revised the discovery method during planning** (flagged explicitly, not
  silently): pure forward SDK traversal can't answer "start at a Route
  Table" or "start at a Private DNS Zone" — those types don't carry
  properties pointing back at what references them. Added a one-shot Azure
  Resource Graph (ARG) reverse index per request so the BFS walks both
  directions; SDK calls still do all node enrichment and the sub-resource
  fetches ARG can't provide (blob containers, PE DNS zone groups, AKS node
  RG's LB/Public IP).
- Wrote `scripts/test_resourcegraph_validation.py` (32 assert-based checks,
  no Azure needed) covering the pure logic — path extraction, category
  classification, reference-map edge extraction, subnet synthesis, CMK URI
  resolution, and `build_graph()`'s BFS/truncation/seed-resolution behavior
  against a mocked `_arg()`.
- **Caught and fixed 3 real bugs before/during real-Azure testing**:
  1. (offline test caught) `forward` edge-map keys used original-case
     resource IDs while `id_map`/`included`/`reverse` used lowercase,
     silently breaking the primary forward-direction lookup. Fixed with one
     `_add_edge()` helper all edge insertion now goes through.
  2. (offline test caught) "Resource Type selected, no Resource Name" — a
     combination the form explicitly allows — silently fell back to
     whole-subscription mode and dropped the type filter. Fixed with a
     dedicated type-only seed-resolution branch.
  3. (real-Azure test caught, offline mocks missed it) ARM sub-resources
     embedded in an array (a NIC's `ipConfigurations[]`) wrap their own
     fields in a *nested* `properties`, not flat on the array item — real
     data has `ipConfigurations[].properties.subnet.id`, not
     `ipConfigurations[].subnet.id`. Fixed generically in `_walk()` (falls
     through into an item's nested `properties` when a key isn't found
     directly) rather than patching every affected reference path by hand.

## Update: Committed the base Resource Relationship Graph feature; then an enterprise UI polish pass

## Work Completed

- Committed the Resource Relationship Graph feature from earlier today as
  `66824be` (only the feature's own files — left the unrelated pre-existing
  uncommitted cosmetic/infra changes and local tool artifacts `.claude/`/
  `graphify-out/` untouched, per this repo's established practice).
- User requested a full enterprise-grade UI polish pass on the graph
  (per-type colors/icons/sizing, hub-centric layout, smart labels, hover
  tooltips + animated path highlighting, an expanded side panel with tags/
  subscription/relationship analysis, search/filter improvements, a stats
  bar, a minimap, glass-card theming, and health-status placeholders) —
  went through Plan Mode given the number of real technical trade-offs
  involved (layout library choice, minimap library, icon strategy), and
  asked the user to choose between two explicit trade-offs before writing
  the plan: **concentric layout, no new dependency** (chosen over
  concentric+fcose) and **add cytoscape-navigator for the minimap**
  (chosen over skipping it) — no viable core-only minimap alternative
  exists.
- Backend (`resourcegraph.py`): added `tags` and `subscriptionId` to the
  ARG projection and `_trim_properties()` (needed for the side panel); a
  new `_hub_vnet_id()` helper builds the hub VNET's resource ID from
  `HUB_SUBSCRIPTION_ID`/`HUB_RESOURCE_GROUP`/`HUB_VNET_NAME` settings alone
  (no extra Azure call), returned as a new top-level `hub_id` field on
  every `build_graph()` response (including the two early-return error
  cases, for a consistent response shape).
- Frontend (`templates/resource_graph.html`, full rewrite of the
  `{% block scripts %}` section): `TYPE_STYLE` map (12 types: color + one
  of 9 hand-drawn inline-SVG icons + size tier), `concentric` layout keyed
  off a computed `level` (hub=100 down to leaf=10), `localStorage`
  position persistence keyed by exact query scope, a custom cursor-follow
  tooltip, hover/select neighborhood highlighting with an animated dashed
  active-path (`line-dash-offset`), a client-side Relationship Analysis
  block (direct/upstream/downstream/impact-if-deleted, computed from
  `GRAPH.edges` — no new backend call), exact-type filter alongside the
  existing category chips, auto-pan/zoom on search match, a stats bar (7
  cards computed from `GRAPH.nodes`), a `cytoscape-navigator` minimap, a
  glass-card theme pass (static translucency + border + shadow — no
  `backdrop-filter`, per `docs/BRANDING.md`'s explicit performance rule,
  flagged to the user as a deliberate deviation from the literal "glass"
  wording), and a health ring derived from `properties.provisioningState`.
- Caught and fixed 2 more real issues during self-review (no browser
  available, so this was careful manual code reading + `node --check`):
  (1) a click-to-select node never actually became Cytoscape-`:selected`,
  so the hover-highlight silently reverted every time the mouse left any
  node even after clicking one — fixed by explicitly calling `.select()`
  in the tap handler and reverting `mouseout` to the selected node's
  highlight instead of clearing outright; (2) the two new offline test
  checks for `hub_id` initially used env-var overrides, which **failed**
  because this sandbox's real DB already has `HUB_*` settings configured
  (DB overrides win over env vars) — fixed by monkeypatching `cfg`
  attributes directly, a more robust test seam regardless of DB state.
- Ran real-Azure re-verification of the two new backend fields: found a
  genuinely-tagged real resource (`rt-GatewaySubnet`, cross-checked via
  `az resource list --query "[?tags != null...]"`) and confirmed the API's
  `tags` output matches exactly; confirmed `hub_id` resolves to the actual
  configured hub VNET in this sandbox.
- `scripts/test_resourcegraph_validation.py`: 32 → 36 checks, all passing.
