## Bugs Fixed (caught during this session's own implementation, before commit)

- `_validate_storage_request` initially referenced `cfg.STORAGE_KINDS` /
  `cfg.STORAGE_SKUS` / `cfg.STORAGE_ACCESS_TIERS` — wrong; these are plain
  module-level constants (like `VM_OS_DISK_TYPES`), not `SETTINGS_SPEC`
  entries, so `cfg.__getattr__` raised `AttributeError`. Fixed by importing
  them directly, matching the `VM_OS_DISK_TYPES` import pattern. Caught by
  the Phase 1 curl-driven submission test (surfaced as a plain error string
  instead of a crash — good evidence the app's error-handling conventions
  work even when *my* new code has a bug).
- `create_storage_account`'s initial `success` computation ANDed across all
  sub-steps (account + blob props + containers) — would have suppressed the
  change-ledger entry (and thus the revert path) for a real, created
  storage account whenever any sub-step failed. Fixed before it was ever
  exercised against a real deploy: `success` now reflects "the account
  exists," with sub-step results carried separately via `all_steps_ok`
  (see the architecture-decisions entry).
- `azure-mgmt-keyvault` / `azure-keyvault-keys` were declared in
  `requirements.txt` (used by the pre-existing AKS CMK feature) but never
  actually installed in this sandbox's venv — not something this session
  introduced, but installing them was needed to verify the Storage feature's
  own Key Vault discovery routes, and incidentally fixes the same gap for
  AKS CMK locally.
