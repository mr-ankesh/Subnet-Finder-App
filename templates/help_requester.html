Requester Guide

How to raise a network request

Everything you can ask for, what to prepare, and how to track it — via the form or the AI assistant.

The basics

The Requester Portal is where you ask the network team for anything on the Azure hub-and-spoke network. Two ways to submit:

  • Form — pick a request type and fill the fields. Best when you know exactly what you need.
  • AI Assistant — describe what you want in plain language; it asks for anything missing and files the request for you.

Every request gets a Request ID — note it down. You can check its status any time with that ID (no login needed for status lookup unless SSO is enabled).

Request types & what to prepare
New VNET
A new spoke VNET / CIDR. Pick a size (/21–/28), the pool, and whether you'll deploy it yourself (we just allocate the CIDR) or the admin deploys it for you. If it needs hub integration, you'll also choose the internet access it needs (none / fully allowed / a specific network rule / a specific application rule) and how many subnets to carve.
Firewall Policy
Add, modify or delete a firewall rule. Network rules take IP/CIDR destinations + ports (e.g. TCP/443); application rules take FQDNs only (e.g. *.example.com) with protocols like https:443.
Hub Integration
Your VNET already exists and only needs hub peering. Provide its subscription, resource group, name, region and address space.
ZPA Routing (R&D / Other / NMO)
Make your spoke reachable via a ZPA connector. Provide your spoke VNET name, CIDR and route-table details. NMO routing also updates the NSG and firewall allow/deny lists — the admin handles all the steps.
New Subnet in Existing VNET
Carve an additional subnet in an already-onboarded VNET — give the VNET name and the subnet size/purpose.
DNS
Three kinds: Add an A/CNAME record in a private zone (needs a description for the audit trail); Link your zone to the Hub (checks the hub doesn't already have it); Link a Hub zone to your VNET (checks the zone exists in the hub, then takes your VNET details). The availability check is mandatory for the link kinds.
VNET Decommission
Retire a spoke. You'll confirm whether it was created via this portal and whether you made manual changes — if you did, remove them first (extra subnets, NSGs, private endpoints, attached devices, peerings). The admin verifies in Azure before deleting anything.
Other
Anything that doesn't fit the above — describe it and set a priority.
After you submit
  • Track it — use Check Status with your Request ID. The status advances automatically as the admin completes each step.
  • New VNET, self-deploy — once the CIDR is assigned, deploy your VNET, then mark it VNET Created with the details so the admin can peer it to the hub.
  • Reminders — if a request is waiting, you can send the admin a reminder from the status view.
  • Notifications — if you gave an email, you'll be notified on key status changes (and via Teams if configured).
Tips
  • Have the Azure identifiers ready (subscription ID, resource group, VNET name) for anything the admin deploys or integrates.
  • Application firewall rules can only target FQDNs — use a network rule for IP destinations.
  • For DNS zone links, run the availability check first — the request can't be submitted until it passes.
  • Not sure which type? Use the AI Assistant and just describe the outcome you want.
