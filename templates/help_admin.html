Admin Guide

Operating Network Copilot

How requests are processed, the safety model, and what every screen does — for the network operations team.

How it works, in one paragraph
Every Azure change is an imperative Azure SDK call driven by a request's data — no templates or Terraform state. You review a request, click the action(s) it needs, and the tool builds the parameters and calls Azure. Everything is guarded, audited and reversible: dry-run simulates changes, nothing is overwritten or deleted without showing you the current state first, and every mutation is recorded in the change ledger so it can be restored.
First-time setup (in order)
  1. Import the subnet inventory (Import Inventory) — load your current allocations first, or the allocator may hand out ranges already in use.
  2. Settings → Azure Credentials — service principal or managed identity; use Test Connection.
  3. Settings → Hub, Firewall, Routing, ZPA NMO, DNS zones RG — your topology and the rule collection groups/collections admins will pick from.
  4. Settings → AI Agent / LLM — choose one provider (OpenAI / Anthropic / on-prem) and fill only its fields.
  5. Settings → Safety — keep Dry-run ON until you've verified everything end-to-end.
Processing requests

Open a request to see a panel with exactly the actions that request needs. Key behaviours:

  • Status advances automatically from the actions you complete — there's no manual status dropdown. A "Mark Completed — done manually" escape hatch exists (with a required note) for work done outside the portal.
  • Done actions show as disabled "✓ Done" buttons and can't be re-clicked.
  • New VNET / Hub Integration — assign a CIDR, deploy the VNET (carves the requested subnets), peer to hub (peering names are shown and editable), add gateway/ZPA routes, apply the requested internet action, and optionally create a spoke route table (default routes + your extras) assigned to chosen subnets.
  • Firewall requests — check the policy/rule first (a content-based coverage check tells you if the traffic is already allowed), pick the rule collection group & collection, then apply add/modify/delete. Modify/delete always fetch and show the current rule before you confirm.
  • NMO ZPA — five steps (NMO route, spoke route, NSG allow, firewall allow, firewall deny); steps 3–5 fetch and show current state before updating.
  • DNS — fetch zone/record state, then create; if the target already exists you get edit / proceed / reject-with-comment.
  • Decommission — a read-only Azure status check (peerings, subnets, attached devices), then remove resources, then release the CIDR.
Safety model
  • Dry-run (Settings → Safety) simulates every mutating call — a badge shows on action panels when it's on.
  • No silent overwrite/delete — when a rule, route, VNET, peering, zone or record already exists, you see its current state and choose to update, proceed as-is, or reject.
  • Change ledger (Changes) records every mutation with its before/after state and a revert plan — restore any change from there.
  • Cancel / Reject shows the deployed changes it will automatically revert, and takes a comment.
  • Audit trail (Audit) records who did what, when, on which request.
The screens
  • Home — IP pools and the allocator; import inventory.
  • Requests — every request, filterable by type and status; open one to process it.
  • Admin Agent — an AI assistant that can run the same operations conversationally (audited and reversible like the buttons).
  • Audit — the who/what/when trail. Changes — the before/after ledger with per-change revert.
  • Settings — all live config (credentials, hub, firewall, routing, DNS, ZPA NMO, LLM, notifications, authentication, safety). Changes apply immediately.
  • Search — keyword search across requests, VNETs, subnets and the audit trail.
